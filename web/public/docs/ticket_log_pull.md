# 日志拉取

## 功能概述

日志拉取用于从外部平台获取指定门店/POS 的日志或数据库压缩包，支持下载归档、日志内容截取入库和自动 AI 分析。

## 入口

- **独立页面**：日志拉取管理 → 可创建不关联工单的独立拉取记录
- **工单详情**：日志拉取 Tab → 创建关联工单的拉取记录

## 使用方式

1. 点击「新增拉取」按钮
2. 选择或搜索关联工单（可选）
3. 选择环境分组（如 prod / uat）
4. 选择商家，系统会根据环境分组和商家自动匹配子环境及凭证：
   - **生产环境（prod）**：所有商家自动匹配，无需额外选择
   - **UAT 环境（uat）**：不同商家属于不同子环境（uat1/uat2/uat3），选商家后自动匹配
5. 选择门店、POS
6. 配置拉取方式（按时间或按路径）、数据类型（日志/DB）
7. 可选：开启「切日志」以指定时间范围截取入库
8. 可选：开启「自动AI」以拉取完成后自动触发 AI 分析
9. 配置存储方式（本地/FTP）和通知设置
10. 提交后记录状态为「待执行」，后台自动提交申请并进入轮询

## 工单门店信息回填

从工单详情的「日志拉取」Tab 打开提交弹窗时，系统会按以下来源回填商家、门店、POS 和拉取日期：

1. 工单同步保存的 `extraData.logPullHints`（含 AI 统一提取出的门店、POS/SCO 和日志日期）；
2. 最近一次日志拉取记录（手动拉取过的商家、门店、POS 和日期会在此保留，再次打开弹窗时自动回显）；
3. 工单自动化配置 `extraData.ticketAutomation.logPullConfig`；
4. 历史同步字段 `extraData.external_field_mapping.ticketStore`（作为门店原始值兜底）。

说明：

- 多维表格主动拉取等延后处理场景下，AI 提取完成后会重建 `logPullHints`，提取出的日期和机台同样能回填弹窗。
- 手动拉取提交后，参数保存在拉取记录中；后续打开弹窗时记录回显优先于 AI 提取值，即用户最近一次实际使用的参数优先。

门店配置由 `/ticket/log-pull/vendor-store-options` 按当前商家和环境懒加载（门店配置按环境隔离，只返回所选环境的门店），选项显示格式为：

```text
门店名称 [org_no] (sap_org_no)
```

- 如果回填值命中 `org_no`、`storeCode` 或 `sap_org_no`，弹窗会显示对应的完整门店选项；提交给外部日志接口的 `storeId` 统一使用 `org_no`。
- 如果工单中的门店信息不完整，或没有匹配到门店配置，系统会保留原始值显示，并提示用户确认；用户可以直接编辑为正确的 `org_no` 后提交。
- 用户手动切换商家时，旧门店值会清空，避免把其他商家的门店提交到当前商家。
- 用户切换环境分组时，门店列表会按新环境重新加载；已选门店若不属于新环境，系统会提示重新确认 `org_no`。

工单同步自动拉日志时，系统会统一合并任务级日志参数、当前有效 AI 提取结果、同步对象字段、历史 `extraData.log_pull_hints`、规则识别结果和系统默认值。自动化审计中的 `identify`、日志提交请求和自动 AI 使用同一份最终参数；缺少 `vendorId`、`storeId`、`posNo/SCO` 或 `modifyTime` 时只记录跳过原因，不创建无效拉取记录。自动拉日志的门店识别与校验均使用「日志拉取配置 → 拉日志默认值」中默认日志环境的分组部分过滤门店配置，即自动分析环境与日志拉取默认环境一致。

对于自动拉日志，系统在提交前会按"同一工单 + 同一环境/商家/门店/POS/数据类型 + 同一日志时间范围/路径/日期"等实际拉取参数，查看同参数**最新一条**记录的状态，按下面的决策矩阵处理，避免工单被编辑后反复拉取相同日志或反复创建注定失败的拉取：

| 同参数最新记录状态 | 自动拉日志行为 | 自动 AI 分析 | 通知 |
|-------------------|---------------|-------------|------|
| 不存在 / 已取消 | 创建新拉取记录 | 由新记录的自动AI配置驱动 | 按正常流程（成功/失败各通知一次） |
| 拉取中（待执行/提交中/轮询中/下载中/解析中） | 不创建，等待该记录完成 | 若该记录未开启自动AI而本次场景要求AI，会把AI配置补充到该记录，完成后自动触发 | 不发新通知 |
| 成功 | 不创建，复用该记录 | 该记录没有AI任务时触发；已有AI任务（成功/执行中）或最近一次AI失败时跳过 | 不发新通知 |
| 失败 / 程序异常 | 不创建、不触发AI、**不发通知** | 跳过 | 完全静默，仅在工单事件和自动化日志中留痕 |

失败静默的原因：同参数失败记录在失败时已经通知过，外部工单再次同步时不重复创建和打扰。此时若参数错误，可在日志拉取列表中修正参数后**重新拉取**；人工重试产生的新记录会成为"最新记录"，重试成功后自动链路即恢复复用，重试仍失败则继续静默。

进行中的记录若一直卡住（如参数错误导致外部平台长期不出结果），可在列表中**停止**该记录；停止后该记录状态变为「已取消」，同参数自动拉日志会允许重新创建。

`log_pull_hints` 中建议使用以下字段：

- `vendorId`：商家编号；
- `sourceStoreCode`：外部来源中的门店编码，只用于保留来源和与 AI 结果做一致性判断，不一定是日志接口可用的 `org_no`，AI 永远不会反写它；
- `storeId`：日志接口使用的门店 `org_no`，由门店选择规则确定并在提交前按当前商家校验；如果外部 `sourceStoreCode` 是 `sap_org_no` 等业务编码，系统会先按商家映射转换为对应的 `org_no`，不能直接把 SAP 编码提交给日志接口；
- `posNo` / `scoNo`：机台编号；
- `modifyTime`：日志日期，格式为 `YYYY-MM-DD`。

AI 提取门店时，如果 AI 值与 `sourceStoreCode` 相等或 AI 值包含在 `sourceStoreCode` 中，则使用 AI 值更新 `storeId`；如果 AI 值为空或不匹配，则使用 `sourceStoreCode`。没有 `sourceStoreCode` 时，有效 AI 新值可以替换旧 `storeId`，无有效 AI 值时保留旧值。`sourceStoreCode` 始终保持外部原始值，不会被 AI 反写。最终 `storeId` 只有通过当前商家 `org_no` 校验后才会提交日志。若同一商家和同一 `sourceStoreCode` 命中多个不同的 `org_no`，系统会在自动化日志中记录商家、来源编码和全部候选门店（包括 `orgNo`、门店名称和 `sapOrgNo`），并中断自动日志提交，避免把日志发到错误门店；用户确认唯一门店后再手动或重新触发拉取。


| 状态 | 说明 |
|------|------|
| 待执行 | 已创建，等待后台提交外部申请 |
| 提交申请中 | 正在向外部平台提交拉取申请 |
| 轮询处理中 | 已提交申请，等待外部平台生成压缩包 |
| 下载中 | 正在下载日志压缩包 |
| 解析中 | 正在解压并截取日志内容入库 |
| 成功 | 拉取完成 |
| 外部失败 | 外部平台返回失败 |
| 程序异常 | 内部流程异常 |
| 已取消 | 用户手动停止 |

## 拉取人说明

日志拉取列表（管理页与工单详情日志拉取 Tab）提供「拉取人」列，用于区分记录来源：

| 拉取人显示 | 含义 |
|-----------|------|
| 「自动」标签 | 由工单同步自动化链路自动创建（悬停可查看触发场景：外部同步 / 远端拉取 / 多维表格拉取 / 手工创建） |
| 用户名 | 由该用户在页面人工创建 |
| 未知 | 历史存量数据且无法识别来源（可悬停查看记录详情） |

该列不需要任何配置，新建记录自动记录来源；存量数据按记录中是否带有自动化快照自动识别。

## 执行机制

日志拉取采用「提交与轮询解耦」的架构：

- **提交申请**：创建记录后由后台线程池快速提交外部申请（瞬时完成，不长期占线程），成功后写入轮询截止时间
- **轮询探测**：由 Celery 周期任务「日志拉取周期扫描」批量扫描轮询中的记录，单次查询外部平台结果（任务键 `module_task.scheduler_maintenance.scan_log_pull_records`，需在「系统监控-定时任务」手动配置，建议每 30 秒执行）：
  - 命中可下载结果 → 投递下载解析
  - 外部返回失败 → 标记失败
  - 超过轮询截止时间（pollTimeoutSec，默认 1800 秒）→ 标记「轮询外部平台超时」失败
- **下载解析**：命中结果后由后台线程池下载压缩包并截取入库（短任务，不长期占线程）

因此任务提交与轮询探测**不受并发数限制**，可批量提交大量记录平铺消化；仅下载解析阶段复用线程池，并发不阻塞提交。

## 操作说明

- **跳转工单详情**：日志拉取管理列表中，记录如果存在「关联工单」，点击该列的工单编号/标题区域会在新标签页打开对应工单详情页；没有关联工单的记录仍显示“-”，不可点击
- **查看日志**：成功/带内容的记录可查看截取的日志文本；首次查看需要准备文件时，按钮会显示环形进度。关闭弹窗或离开页面后重新进入，会恢复同一记录的准备状态和下载百分比，不会重复发起下载
- **复制**：复制已有记录的拉取参数快速创建新记录
- **停止**：停止正在执行中的任务（待执行/提交中/轮询中/下载中/解析中），停止后记录标记为「已取消」，保留已有进度，可重新拉取
- **重新拉取**：用原参数重新提交拉取任务
- **重新下载**：重新下载日志压缩包并覆盖原归档
- **删除**：删除记录并清理关联文件

## 配置项

日志拉取相关配置统一收纳在 **工单同步自动化 → 日志拉取配置** Tab 下，按作用域分为三组卡片：**拉日志默认值**、**存储与资源限制**、**日志拉取外部接口配置**。

### 拉日志默认值（提交参数默认值）

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| commandDataType | 默认数据类型（1=日志, 2=DB） | 1 |
| fileMaxSize | 单文件最大大小(MB) | 500 |
| zipMaxSize | 压缩包最大大小(MB) | 500 |
| storageMode | 默认存储方式(local/ftp) | local |
| rangeBeforeMinutes | 时间点前回溯分钟数 | 10 |
| rangeAfterMinutes | 时间点后延伸分钟数 | 10 |
| autoAiEnabled | 拉取成功后是否自动发起 AI 分析 | 关 |
| aiAgentCode / aiProviderCode | 自动 AI 分析使用的 Agent/Provider | 空 |

自动 AI 分析触发前，如果关联工单没有填写 `affectedVersionId`，系统会在日志拉取成功后从已入库的日志正文中按「版本提取正则」（见下方存储配置说明）提取版本号，并自动创建或复用版本中心记录后回填工单。通常不需要人工维护发生版本；只有日志正文没有可识别版本号，或版本中心关联失败时，才会记录跳过自动 AI 的原因。

如果自动日志步骤因为“已存在相同参数的成功记录”而被跳过，或当前场景只开启了“自动 AI”但未重新拉日志，系统也会直接复用最近的成功日志记录继续执行同一套版本回填与自动 AI 规则，不再要求必须重新拉到一份新日志。

### 存储与资源限制（运行态护栏）

| 配置项 | 说明 | 默认值 | 范围 |
|--------|------|--------|------|
| maxWorkers | 日志拉取线程池最大并发数，保存后即时生效 | 2 | 1~20 |
| pollIntervalSec | 轮询探测间隔秒数 | 20 | ≥3 |
| pollTimeoutSec | 轮询超时秒数（超过则标记失败） | 1800 | ≥60 |
| downloadTimeoutSec | 单次 HTTP 下载超时秒数 | 300 | ≥30 |
| maxContentChars | 入库文本最大字符数，超出则失败 | 500000 | ≥10000 |
| maxExtractSeconds | 解压阶段最大耗时秒数 | 300 | ≥30 |
| maxExtractFileCount | 解压阶段最大文件数 | 2000 | ≥100 |
| maxExtractTotalBytes | 解压阶段最大总字节数 | 2147483648 | ≥10MB |
| maxSearchSeconds | 日志关键字搜索最大耗时秒数 | 30 | ≥3 |
| maxSearchFileCount | 日志搜索最大扫描文件数 | 1000 | ≥10 |
| maxPythonSearchBytes | Python 降级搜索最大扫描字节数 | 268435456 | ≥10MB |
| mode / localDirectory / ftp | 归档存储方式与目录/FTP 连接 | local | - |
| postDownloadExtractEnabled | 下载完成后自动解压到查看目录 | 关 | - |
| postDownloadVersionExtractEnabled | 解压后自动提取版本号 | 关 | - |
| postDownloadIndexEnabled | 解压后自动生成日志行索引 | 关 | - |
| versionExtractPatterns | 日志版本提取正则（JSON 数组） | 见下方说明 | ≤20 条 |

#### 版本提取正则（versionExtractPatterns）说明

该配置同时作用于两条日志版本提取链路：**日志拉取成功后从入库正文提取**（自动 AI 前置步骤）和**下载完成后处理时从解压文件提取**（需开启 `postDownloadVersionExtractEnabled`）。

- **格式**：JSON 数组，每个元素是一个正则表达式字符串，按顺序取第一个命中的结果；每个正则的**第一个捕获分组**作为版本号（无分组时取整个匹配）。
- **默认正则**：锚定 POS 应用版本日志行特征 `ms_h:1, ms_l:1, ls_h:6, ls_l:8, version:1.1.6.8`，只提取这类行中的版本号（如 `1.1.6.8`），避免误提取 `launcher_version:1.0.6.8`（启动器版本）和 `OpenGL parsed version: 4, 6`（显卡解析版本）。
- **回退规则**：配置为空数组、格式非法或全部正则无法编译时，自动回退到内置默认正则，提取链路不会中断；单条非法正则会被忽略，其余继续生效。
- **示例**：
  - 保持默认：`[]`（或清空文本框）
  - 提取启动器版本：`["launcher_version\\s*[:=]\\s*(\\d+(?:\\.\\d+){2,3})"]`
  - 兼容中文"版本：x.y.z"写法：`["版本[号：:]\\s*([0-9]+(?:\\.[0-9]+){2,3})"]`
- **注意事项**：正则按行匹配（下载后处理链路）或对整段正文匹配（正文回填链路），不需要加 `^`/`$` 锚定整行；建议捕获组限定为 `x.y.z` 起步的数字形态（至少三段），防止把普通数字误识别为版本。

| 配置位置 | 配置项 | 说明 |
|----------|--------|------|

### 外部接口配置（环境分组）

日志拉取的外部接口配置采用**环境分组 → 子环境 → 商家映射**三层模型，入口位于 **工单同步自动化 → 日志拉取配置** Tab 的「日志拉取外部接口配置」卡片。

**配置项说明：**

| 层级 | 字段 | 说明 |
|------|------|------|
| 环境分组 | 名称 | 用户可见的分组名，如"生产环境"、"UAT环境" |
| 环境分组 | 默认子环境 | 商家未匹配到任何子环境时的兜底选择 |
| 子环境 | 名称 | 如 UAT1、UAT2 |
| 子环境 | insertUrl | 日志录入接口地址 |
| 子环境 | pageUrl | 页面列表查询地址 |
| 子环境 | 凭证绑定 | 从统一凭证管理中选择的 HTTP Cookie/Header 凭证绑定 |
| 子环境 | origin | 请求 Origin 头 |
| 子环境 | 商家范围 | 选择"★ 全部商家"覆盖所有，或指定具体商家 venderNo |

**匹配规则：**
- prod 环境通常所有商家在同一个子环境，商家范围设为「全部商家」
- UAT 环境不同商家分布在不同子环境（uat1/uat2/uat3），分别配置商家范围和凭证
- 日志拉取时，用户只需选择环境和商家，系统自动匹配到正确的子环境和凭证
- 一个商家可能匹配到多个子环境，此时用户手动选择

**配置示例：**

```
gruop: "uat"
  ├─ uat1 → 凭证绑定A → 商家范围: [10001, 10002]
  ├─ uat2 → 凭证绑定B → 商家范围: [10003, 10004]
  └─ uat3 → 凭证绑定C → 商家范围: [10005]
```

### 门店配置管理（按环境隔离）

门店配置入口：日志拉取管理页 →「门店配置」按钮，弹窗内可查询、导入门店。

**环境归属：**

- 每条门店配置都归属一个**环境分组**（与「拉日志默认环境」使用的环境分组同源），同一门店（商户+机构+SAP 编号相同）可在不同环境下各配置一条
- 弹窗查询区支持按环境筛选，列表展示「环境」列；不选环境时显示全部环境的门店
- 拉取日志弹窗选择环境后，门店下拉只显示该环境下配置的门店；自动拉日志识别门店时也只使用默认日志环境下的门店配置

**导入门店配置：**

1. 点击「下载模板」获取 Excel 模板（表头与原有格式一致，无环境列）
2. 点击「导入配置」打开导入弹窗，**先选择要导入到的环境**，再选择导入方式和文件
3. 导入方式说明：
   - **增量导入**：按 `环境 + 商户编号 + 机构编号 + SAP机构编号` 匹配，已存在则覆盖原记录，否则新增
   - **覆盖导入**：先清空**所选环境**的旧数据再导入，其他环境的配置不受影响
4. 导入完成后显示新增/更新/失败条数，失败行会列出原因

**注意事项：**

- 导入时必须选择环境；不选环境无法提交
- 历史存量门店（未归属环境）只能在「全部环境」查询中看到；如需在指定环境下生效，请重新导入一次并选择该环境
- 门店下拉选项为空时，检查当前环境下是否存在该商家的门店配置；必要时切换环境或重新导入

## 注意事项

- 停止任务采用协作式取消，已在执行的 HTTP 请求可能需要等待当前步骤完成后才停止
- 停止后的记录仍可重新拉取
- 需要保证 Celery beat/worker 运行，且已在「系统监控-定时任务」手动配置「日志拉取周期扫描」任务（任务键 `module_task.scheduler_maintenance.scan_log_pull_records`，interval 30 秒），否则轮询中的记录不会被探测
- 服务重启后，轮询中/待执行的记录由周期任务继续处理，不会丢失；下载/解析中断的记录会清理为失败
- 删除记录会同步清理本地/FTP 上的归档文件
