# 相似工单向量刷新 quality_status 非空约束报错修复

## 问题背景

自相似工单配置新增索引质量状态（`quality_status`）列后，详情页"相似工单"区域偶发报错：

> 相似工单查询失败：(pymysql.err.IntegrityError) (1048, "Column 'quality_status' cannot be null") ...

触发条件是：工单已存在向量记录，且因内容或配置变化需要刷新该记录。详情页打开时系统检测到向量过期（stale）后会自动同步刷新，刷新走"更新已有记录"的数据库语句，此时写入的质量状态为 NULL，违反非空约束导致更新失败。由于哈希算法随向量字段方案调整而变化，存量向量基本都会被判定过期，因此该问题在详情页高频复现。

## 根因说明

- `embedding_record` 表的 `quality_status` 列为非空列，数据库默认值 `ready` 仅对新增行生效；
- 向量刷新时构造的新记录对象未显式赋值该字段，对象属性为 None；
- 数据访问层的"新增或更新"逻辑在已有记录时直接用新对象属性覆盖旧行，Python 侧的 ORM 默认值对这种更新不生效，最终更新语句写入 NULL 报 1048。

全新工单（无历史向量记录）走新增分支不受影响；受影响的均为已有向量的工单刷新场景，包括：

- 工单详情页相似工单查询（检测到向量过期后自动刷新）；
- 工单协同消息面板的相似工单推荐；
- 相似案例索引（草稿/已验证）；
- 手动创建、手动更新、关闭生成知识、外部同步后的向量刷新；
- 相似工单向量手动重建。

## 修复内容

在向量化服务构造向量记录处（`server/modules/ticket/service/ai/ticket_embedding_service.py`）显式赋值 `quality_status="ready"`，不再依赖隐式默认值。同时在单元测试中新增回归用例：断言构造的向量记录必须携带非空 `quality_status`，防止后续改动再次引入同类问题。

## 影响范围

- 仅修复写入时的字段赋值，不改变相似度检索、重排和案例匹配的任何行为；
- 不需要数据修复：数据库 DDL 自带默认值 `ready`，存量行已经是 `ready`，问题只发生在更新语句写入 NULL 的瞬间；
- 修复后详情页相似工单、消息面板、案例索引、向量重建等刷新场景恢复正常。

## 后续建议

由于向量文本方案已从旧版字段切换到新版字段，存量向量在修复前长期停留在旧方案。建议修复上线后执行一次全量向量重建（工单管理 → 相似工单配置 → 向量重建，支持后台执行），把所有向量统一到新方案，避免新旧方案向量混用导致相似度匹配不准。若配置的是外部 Embedding 服务，重建前请关注 Token 消耗。

## 验证结果

- `ruff check` 通过；
- `tests/test_ticket_embedding_service.py` 全部 25 个用例通过，包含新增回归用例；
- 回归用例经验证：临时移除修复时用例失败、恢复修复后通过，确认用例可有效拦截该缺陷。
