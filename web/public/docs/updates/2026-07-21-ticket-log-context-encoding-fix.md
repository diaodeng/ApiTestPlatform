# 工单日志详情中文乱码修复

## 问题

工单日志搜索结果列表中的中文正常，但打开 `2026-07-11_pos.log.4` 的上下文详情后中文显示乱码；同批次的 `2026-07-11_pos.log.5` 正常。

## 排查结果

实际文件 `2026-07-11_pos.log.4` 和 `2026-07-11_pos.log.5` 均为无 BOM 的有效 UTF-8 文件，原始字节中的 `處理成功` 可按 UTF-8 正常还原。`.4` 的前 64KB 恰好落在 UTF-8 中文字符中间，旧探测逻辑将样本末尾的半个字符误判为编码错误，错误返回 `ptcp154` 并写入索引；将 `.4` 按错误编码读取会得到 `铏曠悊鎴愬姛` 这类乱码。

搜索结果会重新探测文件编码，而上下文详情会复用 `.lineidx` 行索引内缓存的编码。旧索引若记录了错误编码，即使日志文件未变化，详情仍会按错误编码读取，造成列表与详情显示不一致。Windows 原生命令读取路径也不能依赖系统默认编码。

## 修复

1. 编码探测改用增量解码，允许样本恰好截断在多字节字符中间，避免有效 UTF-8 被误判。
2. 上下文读取前重新探测当前文件编码；索引的大小、修改时间、版本或编码任一不一致时，自动重建 `.lineidx`。
3. Windows 原生上下文读取使用探测出的编码创建 `StreamReader`，并以 UTF-8 输出，避免无 BOM UTF-8 被 PowerShell 系统默认编码误读。
4. 日志记录会输出索引编码不一致及重建原因，便于后续排查。

## 验证

使用 UTF-8 中文日志构造错误的 GB18030 索引缓存，验证上下文读取会自动重建索引，并返回正确的 `處理成功` 文本；另覆盖 64KB 样本在中文 UTF-8 字符中间截断的识别边界。
