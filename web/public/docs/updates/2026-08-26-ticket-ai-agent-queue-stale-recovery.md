# 工单 AI Agent 队列陈旧请求自动恢复

## 问题

生产环境在 2026-08-26 下午排查时发现，部分工单 AI 分析请求会长期停留在“等待 Agent 槽位”。日志里常见特征是：

- `active_count=0`，说明当前没有正在执行的 Agent 任务；
- `queue_head` 长时间固定为同一个历史请求；
- 服务刚发布或 WebSocket 已断开后，后续新请求仍被旧队列头阻塞。

同时，排队中的 AI 请求会继续持有完整 prompt、上下文和结构化载荷；当积压较多时，会放大 API 进程的内存占用。

## 处理

本次修复保持单 Agent 并发控制不变，只做最小可回滚调整：

1. **补充排队心跳租约**  
   队列中的请求会周期性刷新 `queueLeaseUntil`。若等待协程因服务重启、进程异常或连接中断提前退出，队列头在租约到期后会被自动清理，不再必须等到整笔请求总超时。
2. **补充队列头自愈判断**  
   在抢占 Agent 槽位前，服务端会自动清理以下陈旧队列头：
   - 请求缓存已不存在；
   - 请求状态已经进入终态；
   - 排队租约已过期；
   - 已超过总超时且不存在运行中租约。
3. **优化排队阶段内存占用**  
   请求进入队列后，只保留轻量状态信息；完整请求体在真正拿到 Agent 槽位后再从 Redis 恢复，减少多个等待协程同时持有大体积 AI 载荷造成的内存增长。
4. **降低等待日志噪音**  
   “等待 Agent 槽位”日志改为按固定间隔输出，便于从日志中识别真实卡点，避免排队时高频刷屏。

## 影响范围

- 工单手动 AI 分析
- 工单自动 AI 分析
- Agent 跨进程派发与排队链路

## 使用建议

- 如果日志持续出现“等待 Agent 槽位”且 `active_count=0`，优先检查同一时段的 `queue_head` 是否长期不变。
- 发布修复后，新请求会自动清理失效队列头；如线上已出现历史积压，可结合运维窗口检查对应 Agent 的 Redis 队列键。
- 本次修复不提升并发数；如确有吞吐压力，请再结合 `ticket.ai.agent.maxConcurrentTasks` 单独评估。
