# 工单日志拉取记录独立查看说明

## 背景

同一个工单可能存在多条日志拉取记录。原日志查看器只按 `ticketId` 准备和读取 `data/logs/ticket_{ticketId}/extract`，如果用户先查看过 A 记录，再点击 B 记录，后端会复用已存在的工单级解压目录，导致页面显示 A 记录的日志。

## 本次变更

1. 日志查看准备接口 `POST /ticket/logs/prepare` 新增可选 `recordId`。
2. 日志文件列表、关键字搜索、时间搜索、上下文读取、异常摘要接口都支持可选 `record_id/recordId`。
3. 指定记录查看时，后端目录改为 `data/logs/ticket_{ticketId}/record_{recordId}/source` 与 `extract`，同一工单不同拉取记录互不复用下载缓存和解压目录。
4. 未指定记录时仍兼容旧的工单级目录 `data/logs/ticket_{ticketId}`，避免影响列表页按工单查看最新日志的入口。
5. 前端在工单详情拉取记录表点击“查看日志”时会把当前行 `id` 传给准备、搜索、异常摘要和上下文接口。

## 日志拉取成功后的动作

日志拉取任务成功链路如下：

1. 查询或提交外部日志平台任务，并轮询外部结果。
2. 拿到 `commandResult.url` 后下载原始压缩包。
3. 按记录自身的存储配置保存到本服务归档位置：本地路径或 FTP 路径，并写入该记录的 `storage_path`。
4. 如果记录带有日志时间范围，服务端会解析压缩包中的目标日志条目，截取时间范围内内容并压缩写入数据库 `compressed_content`。
5. 如果记录没有日志时间范围，只保存整包归档和压缩包文件数，不截取正文，后续 AI 可使用整包。

日志查看器的准备目录只服务于“在线搜索/上下文查看”，不会改变记录的原始归档。指定记录已准备过目录时，重复查看不会再次下载或解压。

## AI 分析使用哪条日志

后端已有选择规则：

- 请求带 `logPullRecordId` 时，使用指定日志拉取记录。
- 请求未带 `logPullRecordId` 时，`TicketAiAnalysisService._resolve_log_pull_record` 通过 `TicketLogPullService.get_latest_summary` 取该工单最新一条日志拉取记录，不限定必须成功。
- 当版本号缺失需要从日志补齐时，会先尝试已选记录，再追加最近一条成功记录作为兜底。

本次前端补齐了显式传参：用户从某条拉取记录打开日志查看器后发起 AI 分析，会默认携带该记录的 `logPullRecordId`，避免多条记录时误用其他记录。

## 影响范围

- 仅影响工单日志查看器和从当前查看记录发起 AI 分析的记录选择。
- 不改变日志拉取、重新拉取、重新下载、归档下载的业务语义。
- 历史已经按工单级目录准备过的缓存仍保留，未指定记录的入口继续可用。
