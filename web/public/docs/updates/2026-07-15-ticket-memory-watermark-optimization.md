# 工单大数据量内存水位优化

## 背景

重新部署后服务基础内存约 800M，执行飞书多维表格主动拉取、工单详情日志拉取/查看和工单统计后，进程 RSS 会持续抬高且不立即回落。该现象一部分来自 Python 运行时和依赖库的内存池高水位复用，另一部分来自现有链路存在全量 ORM 对象、大文本中间对象和飞书记录一次性累积。

## 本次处理

1. 工单处理统计 DAO 不再查询完整 `Ticket` ORM 对象，改为只读取统计需要的轻量字段：`ticket_id/submit_time/create_time/first_response_at/processed_at/resolved_at/closed_at`。
2. overview 处理指标改为单次遍历轻量行计算，避免为提交、响应、处理、关闭等指标分别构造中间列表。
3. 趋势处理指标复用轻量行，桶内平均首次响应和首次处理耗时改为累计总秒数和数量，不再为每个桶构造临时行列表。
4. 飞书多维表格主动拉取新增分页迭代入口，调度同步链路按页处理并按 record_id 去重，避免先把所有页记录累积成一个大列表。
5. 日志归档实时查看改为直接返回本次截取文本，并使用 `StringIO` 顺序写入命中日志片段，避免“文本 -> gzip/base64 -> 文本”的重复大对象转换。
6. 日志拉取记录新增 `/ticket/log-pulls/{record_id}/content/stream` NDJSON 流式读取接口，后端按 `meta/chunk/done/error` 事件输出文本，避免先构造完整 JSON 响应再返回前端。
7. 前端日志拉取记录页优先使用流式读取接口，边接收边追加显示；接口异常时回退旧 JSON 接口，保持兼容。
8. 后台日志拉取任务结束、日志内容流式读取结束、工单统计 overview/trend 计算结束后主动删除大临时对象并调用 `gc.collect()`，让 Python 尽快回收可释放对象。
9. 日志压缩包下载链路已是流式：外部 HTTP 下载使用 `requests.get(..., stream=True)` 和 `iter_content(1MB)` 写入临时文件，浏览器下载使用 `FileResponse`，不把整个压缩包读入内存。

## 保持不变

1. 现有 API 响应结构不变，统计接口字段、日志内容接口字段和飞书主动拉取结果摘要字段保持兼容。
2. 日志后台入库仍保存 gzip/base64 压缩文本，避免影响历史记录读取和 AI 分析链路。
3. `query_bitable_records` 仍保留列表返回语义，兼容人员催办、汇总通知等旧调用方；新增迭代入口只用于主动拉取大数据量链路。
4. 旧 `/ticket/log-pulls/{record_id}/content` JSON 接口继续保留，供旧前端和流式读取失败后的降级链路使用。

## 内存现象说明

1. 操作后 RSS 不快速回落不等于一定存在持续泄漏。Python、pymalloc、glibc、数据库驱动、压缩/解压库都会保留部分内存块供后续复用，进程 RSS 常表现为高水位。
2. 真正需要处理的是大对象峰值：完整 ORM 列表、完整飞书记录列表、完整解压文本、完整 JSON 响应体、压缩包一次性读入等。本次改动优先把这些链路改为分批、流式或尽早脱引用。
3. HRM 异常统计 `/hrm/report/2003976705440768/errorSummary?onlySelf=false` 处理二十多万数据时内存更平稳，主要因为其核心逻辑下推到数据库 `count/group_by` 聚合，Python 侧只接收少量聚合结果；工单统计目前仍有部分指标需要 Python 逐行计算，后续应继续向 SQL 聚合或快照表迁移。

## 后续建议

1. 若统计数据量继续增长，下一步应把处理率、未处理存量、趋势桶统计进一步下推到 SQL 聚合或快照表，减少 Python 侧扫描。
2. 日志内容旧 JSON 接口仍会返回文本正文，超大日志场景应优先使用流式接口；前端当前仍会把最终文本放入 `contentText` 展示，若日志继续增大，下一步应改为虚拟滚动或按行分页，避免浏览器端也长期持有整段文本。
3. gzip/base64 的历史入库内容在读取时仍需要先拿到压缩串，当前优化降低的是解压后大字符串和 JSON 响应峰值；若入库内容继续变大，建议新增按文件落盘索引或对象存储分片格式。
