# 工单同步项目/模块变更覆盖修复

## 背景

外部推送、内网拉取和飞书多维表格主动拉取都会复用工单同步入库逻辑。历史实现中，已有工单再次同步时，如果本次外部数据携带了新的项目或模块文本，但没有解析到有效本地项目/模块 ID，入库更新会继续沿用旧工单的 `project_id`、`module_id`，导致外部项目变化后内部归属仍停留在旧值。

## 调整

1. 外部同步更新已有工单时，只要本次携带项目字段（`ticketVender/projectName/merchantName/projectId/projectCode`），就按本次解析结果覆盖内部项目归属。
2. 本次项目未解析到有效本地 ID 时，清空旧 `project_id`，并把本次外部项目文本写入 `merchant_name`。
3. 外部同步更新已有工单时，只要本次携带模块字段（`ticketModle/moduleName/moduleId/moduleCode`），就按本次解析结果覆盖内部模块归属。
4. 本次模块未解析到有效本地 ID 时，清空旧 `module_id`，并把本次外部模块文本写入 `module_name`。
5. 本次项目字段变化但无法解析商家 ID 时，不再沿用旧 `extra_data.log_pull_hints.vendorId`，避免自动拉日志继续使用旧商家。
6. 远端拉取场景仍不复用公网项目/模块 ID；已有本地工单再次入库时，会清空旧本地 ID 并同步远端最新项目/模块文本。

## 影响范围

- 外部推送接口：`POST /ticket/sync/external`
- 飞书多维表格主动拉取：转换为外部同步模型后复用同一入库逻辑
- 内网二次入站：仍遵循 `remote_pull` 不复用远端 ID 的规则，但会同步远端最新文本

## 验证

- 通过受影响单元测试：项目/模块映射失败保留文本、已有工单旧项目/旧模块覆盖、远端拉取不复用远端 ID。
- 通过 `ruff` 静态检查。
