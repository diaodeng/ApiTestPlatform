# 2026-07-02 工单列表多选筛选与索引模型记录

## 背景

工单列表页原有下拉筛选项多数为单选，组合查询时需要反复切换条件。多选后，前端一次提交多个候选值，后端通过 `IN` 条件过滤，减少人工查询次数。

## 变更范围

- 工单列表页下拉筛选改为多选：状态、处理状态、项目、模块、模块Code、工单类型、根因分类、解决方式、关闭结果、细分问题、是否问题、内部优先级、当前处理人、1线人员、内部负责人。
- 前端多选参数统一按逗号分隔字符串提交，例如 `projectIds=1,2`、`statuses=pending,processing`。
- 后端 `TicketQueryModel` 保留旧单值参数，并新增对应多值参数，兼容历史调用。
- `TicketDao.get_ticket_list` 将多值参数归一化后使用 `IN` 过滤；处理状态多选使用 OR 组合。
- `Ticket` 模型声明列表常用筛选索引，和已手动创建的数据库索引保持一致。

## 性能说明

- 多选筛选本身不会显著增加单次查询复杂度，数据库会把 `IN` 条件作为范围匹配处理。
- 当前列表仍包含关键字模糊查询、JSON 提交时间表达式和最新日志/AI 状态子查询；这些条件在大数据量下仍可能成为主要耗时来源。
- 这次模型侧补齐的组合索引覆盖常用等值筛选字段和 `create_time/ticket_id` 排序兜底，但提交时间仍优先来自 `extra_data.external_sync.externalCreateTime`，普通 `create_time` 索引不能完全覆盖该表达式。

## 后续建议

- 如果工单量继续增长，建议将提交时间落为独立列 `submit_time`，并增加 `(del_flag, submit_time, ticket_id)` 索引。
- 如需继续优化人员筛选体验，可增加“仅我负责/我的团队”这类快捷筛选，避免人员多选过多。
