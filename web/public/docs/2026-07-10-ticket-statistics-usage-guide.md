# 工单统计系统使用指南

## 一、概述

工单统计系统提供两大核心功能：

1. **统计概览（Overview）**：展示指定时间范围内的工单总量、处理率、分类分布等汇总指标。
2. **趋势分析（Trend）**：按天、周、月粒度展示工单新增、处理、关闭等变化趋势。

系统支持两种统计口径：**实时口径**和**快照口径**，适用于不同场景。

---

## 二、统计口径：实时 vs 快照

### 2.1 实时口径（默认）

**定义**：实时查询当前数据库中工单的最新状态，按工单的 `submit_time`（提交时间）归属到查询时间范围。

**特点**：
- 数据实时反映当前最新状态
- 工单状态变化后，历史统计数据会随之改变
- 适合查看当前最新情况

**适用场景**：
- 日常实时监控
- 查看当前工单处理进度
- 临时查询当前状态

**操作方式**：
1. 进入工单统计页面
2. 默认即为"实时口径"，无需切换
3. 或手动选择页面顶部的"实时口径"选项

---

### 2.2 快照口径

**定义**：读取每日冻结的统计快照，数据来自 `ticket_statistics_daily` 表，每个自然日生成一次。

**特点**：
- 数据在快照生成时冻结，后续不会改变
- 即使工单后续状态变化，历史快照保持不变
- 适合生成稳定的周报、月报

**适用场景**：
- 生成周报、月报等定期汇报
- 历史数据对比分析
- 需要口径稳定的统计场景
- 汇总通知推送（默认使用快照口径）

**操作方式**：
1. 进入工单统计页面
2. 点击页面顶部的"快照口径"选项
3. 页面会显示提示："当前使用快照口径，统计结果来自每日冻结快照"

**重要说明**：
- 快照数据由每日定时任务自动生成
- 如果某天没有快照数据，查询结果可能为空
- 历史快照需要手动触发补跑任务才能补齐

## 三、筛选条件说明

### 3.1 通用筛选（两种口径都支持）

| 筛选项 | 说明 | 实时口径 | 快照口径 |
|--------|------|----------|----------|
| **提交时间范围** | 按工单提交时间过滤 | ✅ 生效 | ✅ 生效 |
| **项目** | 按所属项目过滤 | ✅ 生效 | ✅ 生效（聚合叶子维度） |
| **模块** | 按所属模块过滤 | ✅ 生效 | ✅ 生效（聚合叶子维度） |
| **模块业务码** | 按模块业务码过滤 | ✅ 生效 | ✅ 生效（聚合叶子维度） |
| **工单类型** | 按工单类型过滤 | ✅ 生效 | ✅ 生效（聚合叶子维度） |
| **细分问题类型** | 按细分问题分类过滤 | ✅ 生效 | ❌ 不生效 |

**快照口径筛选说明**：
- 快照表按 `项目 + 模块 + 工单类型` 三个维度冻结叶子行
- 筛选时，系统会聚合匹配的叶子维度行
- 细分问题类型未冻结到快照表，因此不参与快照筛选

### 3.2 趋势粒度

趋势分析支持三种时间粒度：
- **天（Day）**：按自然日分桶
- **周（Week）**：默认可按系统参数选择自然周或业务周分桶
- **月（Month）**：按自然月分桶

周粒度新增“周分桶”选项：
- **自然周**：按 ISO 周分桶，周一为一周开始。
- **业务周**：按系统参数 `ticket.statistics.time.config` 中的业务周起点分桶，默认周四 18:00。

快照口径下，自然日、自然周和自然月继续读取 `ticket_statistics_daily` 自然日快照后聚合；`快照口径 + 周粒度 + 业务周` 读取 `ticket_statistics_period_snapshot` 业务周周期快照，可按周四 18:00 等非自然日边界精确统计。

## 四、统计指标详解

### 4.1 概览卡片

| 指标 | 含义 | 计算方式 |
|------|------|----------|
| **总量** | 查询范围内的工单总数 | 提交时间在查询范围内的工单数量 |
| **新增** | 查询时间内新增的工单数 | 提交时间落在查询范围内的工单数量 |
| **新增已处理** | 新增工单中已处理的数量 | 新增工单且 `processed_at` 非空的工单数 |
| **处理率** | 新增工单的处理完成率 | 新增已处理数 ÷ 新增数 × 100% |

### 4.2 时间字段语义

| 字段 | 语义 | 写入时机 |
|------|------|----------|
| `submit_time` | 工单业务提交时间 | 创建时写入，外部同步取外部 `createTime` |
| `first_response_at` | 首次响应/接手时间 | 指派处理人时写入 |
| `processed_at` | 首次形成有效排查结论时间 | 状态流转到 `wait_release` 或保存 RCA 时写入 |
| `resolved_at` | 工单处置完成时间 | 进入任意终态时写入 |
| `closed_at` | 工单正式关闭时间 | 状态流转到 `closed` 时写入 |

### 4.3 统计分布块

概览页展示多种分类分布统计：

- **问题性质分布**：Bug vs 非 Bug 工单数量
- **工单类型分布**：按工单类型分类统计
- **模块分布**：按所属模块统计 Top 模块
- **细分问题分布**：按细分问题类型统计 Top 问题
- **根因分类分布**：按根因分类统计
- **解决方式分布**：按解决方式统计
- **关闭结果分布**：按关闭结果统计
- **处理人分布**：按处理人统计工单数量

### 4.4 趋势指标

每个趋势桶（天/周/月）包含以下指标：

| 指标 | 含义 |
|------|------|
| **新增** | 该桶内提交的工单数 |
| **已响应** | 该桶内首次响应的工单数 |
| **已处理** | 该桶内形成处理结论的工单数 |
| **新增已处理** | 新增工单中在该桶时间内已处理的数量 |
| **处理率** | 新增已处理数 ÷ 新增数 |
| **处置完成** | 该桶内处置完成的工单数 |
| **关闭** | 该桶内关闭的工单数 |
| **净增** | 新增数 - 关闭数 |
| **未处理存量** | 截止到该桶末，累计未处理工单数 |
| **未关闭存量** | 截止到该桶末，累计未关闭工单数 |
| **平均响应耗时** | 该桶内首次响应工单的平均耗时（从提交到响应） |
| **平均处理耗时** | 该桶内已处理工单的平均耗时（从提交到处理） |
| **Top 细分问题** | 该桶内最常见的细分问题类型 |
| **Top 模块** | 该桶内工单最多的模块 |

## 五、每日快照任务

### 5.1 任务说明

**任务名称**：`ticket_daily_statistics_snapshot`

**执行频率**：默认每日执行（建议 23:55 或次日 00:05）

**默认统计**：昨天（`date.today() - 1`），确保统计完整自然日数据

**任务职责**：
1. 统计指定日期的工单指标
2. 生成全局快照（`snapshot_scope=all`）
3. 生成叶子维度快照（`snapshot_scope=leaf`），按 `项目 + 模块 + 工单类型` 分组

### 5.2 快照数据结构

每日生成的快照包含：

- **1 条全局快照**：`snapshot_scope=all`，`project_id=0`，`module_id=0`，`issue_type_id=''`
- **N 条叶子维度快照**：`snapshot_scope=leaf`，每条对应一个唯一的 `项目+模块+工单类型` 组合

### 5.3 手动触发快照

任务支持三种调用模式：

**模式一：默认（不传参）— 统计昨天**

适用于日常定时执行，默认统计昨天的快照数据。

```json
{}
```

**模式二：指定单天（传 `statistics_date`）**

统计指定日期的快照数据，适用于补跑某一天的快照。

```json
{
  "statistics_date": "2026-07-01"
}
```

**模式三：日期范围（传 `begin_date` + `end_date`）**

逐日统计指定日期范围内的快照数据，适用于批量补跑历史数据。

```json
{
  "begin_date": "2026-06-01",
  "end_date": "2026-06-30"
}
```

范围模式每天独立 commit，某天失败不影响其他天。返回结果包含：
- `total_days`：处理天数
- `total_leaf_count`：总 leaf 快照数
- `failed_days`：失败日期列表（空表示全部成功）

**操作步骤**：

1. 进入系统管理 → 定时任务
2. 找到 `ticket_daily_statistics_snapshot` 任务
3. 手动执行，根据需要在参数中填入上述 JSON
4. 查看执行结果确认快照是否生成

### 5.4 快照幂等性

快照任务支持重复执行（upsert 幂等）：
- 同一天的快照会覆盖更新
- 不会重复插入数据
- 可以安全地重新生成历史快照

### 5.5 调度时间建议

- **推荐 23:55 执行**：统计"昨天"的数据，此时昨天的自然日已接近结束，数据基本完整。
- **凌晨 00:05 执行**：同样默认统计"昨天"，效果一致，确保前一天数据完整。
- **关键点**：任务默认目标是"昨天"而非"今天"，因此无论 23:55 还是次日凌晨执行，都能正确覆盖完整自然日数据。
- **不推荐"统计今天"**：如果任务在 23:55 执行但统计"今天"，会丢失 23:55~24:00 之间提交的数据。统计"昨天"则无此问题。

### 5.6 业务周快照任务

**任务名称**：`ticket_business_week_statistics_snapshot`

**默认统计**：上一完整业务周，业务周起点来自系统参数 `ticket.statistics.time.config`，默认周四 18:00。

**任务职责**：
1. 按业务周开始和结束时间统计完整周期。
2. 写入 `ticket_statistics_period_snapshot` 表。
3. 生成全局行和 `项目 + 模块 + 工单类型` 叶子维度行。

手动执行示例：

```json
{}
```

补跑单个业务周：

```json
{
  "period_start_time": "2026-07-09 18:00:00"
}
```

如果只传日期，例如 `"2026-07-09"`，任务会自动使用当前配置的 `businessWeekStartTime` 补齐为 `2026-07-09 18:00:00`。

## 六、版本治理与版本统计

工单列表页提供版本治理入口，用于维护已修复、已发版和已验证工单的版本闭环信息。

### 6.1 批量维护

操作步骤：

1. 进入工单列表页。
2. 勾选需要维护的工单。
3. 点击“版本批量维护”。
4. 填写计划修复版本、实际修复版本、实际发版版本、发版时间或验证时间。
5. 如需快速闭环，可勾选“标记为已发版”或“标记为已验证”。未填写时间时，后端使用当前时间。

说明：

- 空字段不会覆盖原工单字段。
- 标记发版完成会写入 `DEPLOYED` 工单事件。
- 标记验证完成会写入 `VERIFIED` 工单事件。

### 6.2 版本统计

工单列表页点击“版本统计”可按当前筛选条件实时聚合版本维度。

统计分为两类：

- **发生版本**：用于观察哪个版本问题多，包含工单数、真实问题数、Issue 数、未处理数、未关闭数、Top 模块、Top 工单类型和 Top 根因。
- **修复/发版版本**：用于观察哪个版本解决了什么问题，包含工单数、Issue 数、已发版数、已验证数、未验证数、关闭结果、解决方式和细分问题。

当前版本统计是实时口径，读取 `ticket` 当前态聚合。若后续用于正式周报，建议新增版本维度快照表，避免历史统计受后续字段维护影响。

范围补跑：

```json
{
  "begin_time": "2026-06-25 18:00:00",
  "end_time": "2026-07-09 18:00:00"
}
```

范围模式按 7 天步进，每个业务周独立 commit，某周失败不影响后续业务周。

## 六、数据流转流程

### 6.1 实时统计流程

```
用户查询统计页
    ↓
前端调用 GET /ticket/statistics/overview?statisticsMode=realtime
前端调用 GET /ticket/statistics/trend?statisticsMode=realtime
    ↓
后端查询 ticket 主表
    ↓
按 submit_time 过滤工单
    ↓
实时计算各项指标
    ↓
返回结果给前端展示
```

### 6.2 快照统计流程

```
每日定时任务触发
    ↓
TicketStatisticsSnapshotService.build_daily_snapshot()
    ↓
统计当天所有工单的各项指标
    ↓
写入 ticket_statistics_daily 表（全局 + 叶子维度）
    ↓
用户查询统计页（选择快照口径）
    ↓
前端调用 GET /ticket/statistics/overview?statisticsMode=snapshot
前端调用 GET /ticket/statistics/trend?statisticsMode=snapshot
    ↓
后端查询 ticket_statistics_daily 表
    ↓
按筛选条件聚合叶子维度行
    ↓
返回结果给前端展示
```

### 6.3 汇总通知流程

```
每日汇总通知定时任务触发
    ↓
读取通知配置，默认 statisticsMode=snapshot
    ↓
调用统计服务获取快照口径数据
    ↓
生成通知内容
↓
推送到指定飞书群
```

### 6.4 业务周快照统计流程

```
业务周结束后定时任务触发
    ↓
TicketStatisticsSnapshotService.build_business_week_snapshot()
    ↓
按业务周开始/结束时间统计完整周期
    ↓
写入 ticket_statistics_period_snapshot 表（全局 + 叶子维度）
    ↓
用户查询统计页（快照口径 + 周粒度 + 业务周）
    ↓
GET /ticket/statistics/overview?statisticsMode=snapshot&weekBucketMode=business_week
GET /ticket/statistics/trend?statisticsMode=snapshot&granularity=week&weekBucketMode=business_week
    ↓
后端查询 ticket_statistics_period_snapshot 表
    ↓
返回精确业务周快照结果
```

## 七、常见问题

### Q1: 为什么快照口径和实时口径的数据不一致？

**A**: 这是正常的。快照口径是历史冻结数据，实时口径是当前最新数据。如果工单状态在快照生成后发生了变化，两者就会不一致。

### Q2: 快照口径下，细分问题类型筛选为什么不生效？

**A**: 快照表按 `项目+模块+工单类型` 三个维度冻结，未包含细分问题类型。如需按细分问题筛选，请使用实时口径。

### Q3: 如何确保快照数据完整？

**A**: 确保 `ticket_daily_statistics_snapshot` 定时任务正常运行。如果某天缺失快照，可以手动执行任务并指定日期参数。如需批量补跑，使用 `begin_date` 和 `end_date` 参数一次补跑多天。

业务周统计还需要确保 `ticket_business_week_statistics_snapshot` 正常运行。历史业务周缺失时，使用 `period_start_time` 或 `begin_time/end_time` 补跑。

### Q4: 处理率的计算口径是什么？

**A**: 处理率 = 新增已处理数 ÷ 新增数。其中"新增已处理"指新增工单中 `processed_at` 非空的工单数量。

### Q5: 为什么"已处理"和"新增已处理"数量不同？

**A**: 
- **已处理**：该时间内所有形成处理结论的工单（包括历史工单）
- **新增已处理**：该时间新增的工单中，已形成处理结论的数量

### Q6: 趋势图中的"未处理存量"怎么理解？

**A**: 截止到该时间桶末，累计提交但尚未形成处理结论的工单总数。反映积压情况。

### Q7: 如何选择使用实时口径还是快照口径？

**A**: 
- **实时口径**：日常监控、查看当前进度、临时查询
- **快照口径**：生成周报月报、历史对比、需要稳定口径的场景

### Q8: 快照任务执行失败怎么办？

**A**: 
1. 检查后端日志，定位失败原因
2. 修复问题后，手动执行任务补跑缺失日期的快照
3. 快照任务支持重复执行（upsert 幂等），不会重复插入数据
4. 如果连续多天缺失，使用范围模式 `begin_date` + `end_date` 一次性补跑

## 八、最佳实践

### 8.1 日常监控

使用**实时口径**，关注：
- 当前未处理存量（积压情况）
- 今日新增和处理情况
- 处理率趋势

### 8.2 周报生成

使用**快照口径**，关注：
- 本周新增、已处理、处理率
- 趋势变化
- Top 模块和问题分布

### 8.3 月度汇报

使用**快照口径**，趋势粒度选择"月"，关注：
- 月度新增和处理趋势
- 处理率变化
- 存量变化趋势
- Top 问题和模块变化

### 8.4 问题复盘

使用**实时口径**，结合细分问题类型筛选：
- 按细分问题类型查看分布
- 分析 Top 细分问题趋势
- 定位需要重点改进的问题类型

## 九、技术参考

### 9.1 相关接口

- `GET /ticket/statistics/time-config`：统计默认时间配置
- `GET /ticket/statistics/overview`：统计概览
- `GET /ticket/statistics/trend`：趋势统计

### 9.2 核心参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `beginTime` | string | 开始时间（YYYY-MM-DD 或 YYYY-MM-DD HH:mm:ss） |
| `endTime` | string | 结束时间 |
| `statisticsMode` | string | `realtime` 或 `snapshot` |
| `projectIds` | string | 项目ID，逗号分隔 |
| `moduleIds` | string | 模块ID，逗号分隔 |
| `moduleCodes` | string | 模块业务码，逗号分隔 |
| `issueTypeIds` | string | 工单类型编码，逗号分隔 |
| `problemPatternCodes` | string | 细分问题类型编码，逗号分隔（仅实时口径生效） |
| `granularity` | string | 趋势粒度：`day`、`week`、`month` |
| `weekBucketMode` | string | 周分桶：`calendar_week`、`business_week` |

### 9.4 默认时间配置

系统参数：`ticket.statistics.time.config`

默认值：

```json
{
  "defaultRangeMode": "business_week",
  "rollingDays": 7,
  "businessWeekStartWeekday": 4,
  "businessWeekStartTime": "18:00:00",
  "businessWeekDefaultWindow": "current",
  "trendWeekBucketMode": "business_week"
}
```

说明：
- `rolling_days` 文案显示“最近 N 天”，不再称为“最近一周”。
- `business_week + current` 显示“当前业务周”。
- `business_week + previous_completed` 显示“上一完整业务周”。
- 页面首次进入和点击“重置”都会恢复该默认范围。
- 业务周默认范围会保留具体时分秒，例如 `2026-07-09 18:00:00` 至 `2026-07-16 17:59:59`。
